# 检查规则详解

每条规则给出：**判定方式**、**为什么是问题**、**误报场景**。

严重度定义：

- `error` —— 一定会导致解析错误或数据错误，必须修
- `warn` —— 大概率是错误，但可能是有意设计，需要人确认
- `info` —— 提示性，通常是历史遗留或约定问题

---

## ENC-001 · 文件不是 UTF-8

**判定**：先试 UTF-8，失败则试 GBK；若 GBK 成功则报错，若不是 UTF-8 就先判定为非 UTF-8。

**为什么**：DBC 没有编码声明，靠猜。国内供应商常用 GBK 写中文注释（`CM_`）。表现：

- Vector CANoe / CANdb++ 正常显示
- Python `open(f)` 默认 UTF-8 → `UnicodeDecodeError`
- `cantools` 会**静默跳过**坏字节 —— 看起来正常，注释全丢
- git diff 把整个文件当二进制

**真实案例**：某前灯矩阵在 offset 27075 处出现 `\xa3\xa8`（GBK 全角括号），UTF-8 解码在此中断。因为 cantools 容忍，问题一直没被发现，直到有人写脚本处理注释。

**误报**：几乎不会。若文件确实需要用 GBK 交付，`--min-severity warn` 可忽略。

**修法**：

```bash
python dbc_analyze.py fix-encoding in.dbc out.dbc
```

## BIT-001 · 位域重叠

**判定**：展开每个信号的**每一个 bit**的 `(字节号, 位号)` 坐标，同一帧内若两个信号占据同一坐标即报。

Motorola（大端）位序推进规则：`pos + 15 if pos % 8 == 0 else pos - 1`；Intel（小端）为 `pos + 1`。

**为什么**：两个信号抢同一位，收发两端都「能跑」，但至少有一个永远解出错误值。这类错在 CANoe 里不报错，只有对比物理值时才暴露。

**误报**：

- 复用信号（multiplexed，`SG_ xxx m0 :`）本来就在同一位上按多路复用值区分 —— 当前版本会**误报**，因为还没实现 mux 感知。遇到 `MUX-001` 提示时需人工确认。
- 显式覆盖（overlay）设计极为罕见，一般不是有意为之。

## RNG-001 · 信号越界

**判定**：信号占据的最大字节号 × 8 是否 ≥ `DLC × 8`。

**为什么**：DBC 里写着 64 bit 的帧，某个信号起始位却在 byte 15（需要 16 字节）。生成代码时会写越界，或者被静默截断。

**误报**：几乎没有。若 DLC 本身非法（见 `DLC-001`），这条会连带来，先修 DLC。

---

## DLC-001 · 非法 DLC

**判定**：DLC 不在 CAN FD 合法集合内。

合法值：`0-8, 12, 16, 20, 24, 32, 48, 64`。

**为什么**：DLC 必须是上述离散值。写 13 这种值，不同工具行为不一致：有的当 13 字节，有的向上取到 16，有的直接拒绝加载。

**误报**：无。

## ENU-001 · ENUM 属性写成数字

**判定**：`BA_DEF_` 声明为 `ENUM` 的属性，在 `BA_` 赋值时给的是裸数字而非带引号的标签。

```dbc
BA_DEF_ BO_ "GenMsgSendType" ENUM "Cyclic","Event","CyclicAndEvent";
BA_ "GenMsgSendType" BO_ 466 1;        ← 问题：应为 "Event"
```

**为什么**：Vector 工具链按索引容忍。严格实现的解析器会拒绝或回退到 `BA_DEF_DEF_` 默认值 —— 于是「发送类型」静默变成 `Cyclic`，周期性配置全错。

**真实案例**：某矩阵 683 处 ENUM 赋值全是数字，其中 `GenSigASIL` 379 个信号全部赋值为 `5`（对应 `"D"`）—— 等于宣称所有信号都是 ASIL D。这显然不是真实的安全分析结论，而是批量填充的副作用。

**误报**：若属性确实是 INT 类型则不会报。此处只针对 ENUM。

## SYM-001 · 左右不对称

**判定**：找出报文名只差一个「侧别标识」的成对报文（`L`/`R`、`A`/`B`、`LEFT`/`RIGHT`、`LH`/`RH`、`FL`/`FR`、`MFL`/`MFR`、`IN`/`OUT`），把标识归一化为 `X` 后比较信号名集合。

**为什么**：车灯、门控、后视镜这类对称部件，两侧矩阵通常逐信号对齐。一侧多一个信号，另一侧按名字取值的代码会拿到默认 0 —— 表现为「右灯这个功能没反应」。

**误报**：

- **两侧功能本就不同**是真实情况。例如左灯带投影模块、右灯不带，那是设计意图，不是缺陷。工具只能提示，不能判断。
- 命名不规则（`FL` vs `RightFront`）时配对失败，会静默不报。

**建议**：出现此警告时先确认「是不是本来就不该对称」。

## TYP-001 · 命名拼写漂移

**判定**：把侧别标识归一化为 `X` 后，按小写分组；同组内若存在**不同的原始字符串**，说明只差大小写或形状。

**为什么**：这是最阴的一类。`FLM_L_AFSFctst` 与 `FLM_R_AFSFctSt` —— 差一个字母的大小写。按 A 侧名字写的代码在 B 侧永远取不到值，而且**编译器不报错**、**CANoe 不报错**，只在实际功能不生效时才被发现。

**误报**：只差大小写且**确实是两个不同语义的信号**时误报。极为罕见。

**注意**：此规则与 `SYM-001` 常常同时触发 —— 拼写不同必然导致信号名集合不同。两条一起看更清楚：`SYM` 说「不对称」，`TYP` 指出「差在哪」。

## DUP-001 · 跨报文信号重名

**判定**：同一信号名出现在两个及以上报文中。

**为什么**：

- 生成的代码若用 `SignalName` 作为全局标识，会冲突
- 抓包分析时按名字查值会命中错误的帧
- 若两处语义不同，人也会读错

**误报**：有些矩阵**故意**在不同报文复用同名信号表示同一物理量（例如 `VehicleSpeed` 同时在快帧和慢帧中）。此时属于设计选择，需确认。

## STA-001 · 缺少 GenSigStartValue

**判定**：统计显式设置 `GenSigStartValue` 的信号比例。

**为什么**：未设置的信号默认从 0 开始。若某枚举的 `0` 表示 `Init`、`1` 表示 `Off`，上电首帧的状态就与预期不符 —— 例如灯在初始化瞬间被识别为「未定义」而非「关闭」。

**误报**：绝大多数矩阵都不设启动值，所以这条固定为 `info`，只做提醒。

---

## NOD-001 · 发送节点未声明

**判定**：报文发送方不在 `BU_` 列表中（`Vector__XXX` 除外）。

**为什么**：`Vector__XXX` 表示「未知/仿真」，是合法的占位。但如果写了一个具体节点名却没在 `BU_` 声明，做残余总线仿真（rest-bus simulation）时该节点不存在，报文发不出来。

**误报**：无。

---

## VAL-001 · 短信号缺值表

**判定**：长度 ≤ 4 bit、无单位、且没有 `VAL_` 定义的信号。

**为什么**：4 bit 以内且不带物理单位的信号几乎一定是枚举。没有值表，`2` 这个数字对读者毫无意义。

**误报**：位图（bitmap）、计数器低 4 位、保留位都会误报。这条是 `info`，用于提示「这些信号可能需要补文档」。
